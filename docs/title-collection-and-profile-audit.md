# 称号コレクション調査・将来のプロフィール機能に向けた調査レポート

**ステータス: 調査のみ。本書作成の時点でコードの削除・非表示・仕様変更は一切行っていません。**
称号コレクションの廃止判断はこのレポートの内容を確認した上で別途行ってください。

対象ブランチ: `feature/trophy-sticky-header-title-audit`

## 1. 称号コレクションの全体像

### 1.1 称号の総数と全一覧

称号は**12件**(国旗クイズ用6件・首都クイズ用6件)。定義は `js/quiz.js` の `TITLES`/`CAPITAL_TITLES`。

**国旗クイズ(`TITLES`)**

| id | 名称 | 獲得条件 |
|---|---|---|
| beginner | 国旗ビギナー | 10問全問正解 |
| challenger | 国旗チャレンジャー | 20問全問正解 |
| traveler | 国旗トラベラー | 30問全問正解 |
| expert | 国旗エキスパート | 50問全問正解 |
| master | 国旗マスター | 100問全問正解 |
| legend | 国旗レジェンド | 198問全問正解(WORLD COMPLETE) |

**首都クイズ(`CAPITAL_TITLES`)**

| id | 名称 | 獲得条件 |
|---|---|---|
| cap_beginner | 首都ビギナー | 10問全問正解 |
| cap_challenger | 首都チャレンジャー | 20問全問正解 |
| cap_traveler | 世界都市トラベラー | 30問全問正解 |
| cap_expert | 首都エキスパート | 50問全問正解 |
| cap_master | 首都マスター | 100問全問正解 |
| cap_legend | 首都レジェンド | 198問全問正解(WORLD CAPITAL COMPLETE) |

### 1.2 獲得判定が行われる場所

- `js/app.js` のクイズ終了処理(国旗・首都クイズ共通の結果確定箇所、おおむね576行目付近)で、そのプレイが全問正解だった場合に `getTitleByCount(total, mode)` で対象の称号を特定し、`Storage.awardTitleIfNew(titleObj.id, mode)` を呼ぶ。
- 判定はそのプレイ結果(`correct === total` 相当)だけを見ており、新トロフィー(`TrophyModule.evaluate*`)の判定エンジンとは完全に独立した別経路。

### 1.3 保存方式と保存キー

`js/storage.js` の `StorageKeys`/`CapitalStorageKeys`(`keysForMode(mode)` で切替)。

| 論理名 | 国旗クイズのキー | 首都クイズのキー | 内容 |
|---|---|---|---|
| TITLES | `wfq_v1_earned_titles` | `wfq_v1_capital_earned_titles` | `{titleId: {earnedAt}}` |
| ATTEMPTS | `wfq_v1_attempts_count` | `wfq_v1_capital_attempts_count` | 挑戦回数(整数) |
| BEST_RATE | `wfq_v1_best_rate` | `wfq_v1_capital_best_rate` | 過去最高正答率 |
| BEST_RECORDS | `wfq_v1_best_records` | `wfq_v1_capital_best_records` | `{問題数: {correct, total}}` |

公開API: `getEarnedTitles`/`awardTitleIfNew`/`hasTitle`/`incrementAttempts`/`getAttempts`/`updateBestRate`/`getBestRate`/`getBestRecords`/`updateBestRecord`(全て `mode` 引数で国旗/首都を切替)。

### 1.4 既存データの引き継ぎ方法

バージョン管理やマイグレーション処理は無く、キーの値をそのまま読み書きするだけ(`TITLES`/`BEST_RECORDS` はJSON、`ATTEMPTS`/`BEST_RATE` は数値文字列)。壊れたJSONは空オブジェクトとして扱われ、安全側に倒れる。

### 1.5 称号を表示しているすべての画面

1. **称号コレクション画面**(`#screen-collection`、`renderCollectionScreen()`)— トップ画面の「🥇 称号コレクション」から直接遷移。12件の称号バッジに加え、「記録」セクション(挑戦回数・最高正答率・問題数ごとの最高記録)も表示する。
2. **称号獲得画面**(`#screen-title-award`、`renderTitleAwardScreen()`)— 国旗/首都クイズで全問正解した直後、結果画面の「🏅 称号を見る」から遷移。紙吹雪・ファンファーレ演出付き。
3. **記念画像・賞状作成画面**(`#screen-memorial`)— 称号獲得画面の「🖼 記念画像を作る」、または結果画面の同ボタンから直接遷移可能。`titleObj`(称号データ)を使ってメダル画像・賞状画像(canvas)を生成しダウンロードできる。
4. **結果画面**(`#screen-result`)— 全問正解した回だけ、「🏅 称号を見る」「🖼 記念画像を作る」ボタンを表示する条件分岐に `titleObj` の有無を使っている。

### 1.6 ランキングやゲーム結果での利用

- 「世界の国どこかな？」のランキング(`js/findcountry.js`)は称号と**無関係**。別の保存キー(`wfq_v1_findcountry_ranking` 等)・別のデータ構造で、称号システムのコードを一切参照していない。
- 世界地図・世界図鑑も称号を参照していない。
- 国旗/首都クイズの**結果画面**だけが、称号データ(`titleObj`)の有無でボタン表示を切り替えている(1.5参照)。

### 1.7 称号を削除すると影響を受ける機能

称号の「画面」と「データ」で影響範囲が大きく異なります。

- **称号コレクション画面(UI)だけを削除する場合**: 影響は「12件のバッジ＋記録を一覧で見る手段が無くなる」ことのみ。データの記録(称号獲得・挑戦回数・最高記録の更新)は結果画面側のクイズ終了処理で行われており、コレクション画面のコードとは独立しているため、画面を消してもデータの記録自体は止まりません。
- **称号のデータ(Storage)まで削除・無効化する場合**: 下記2章のとおり、**153件中45件のトロフィー**がこのデータを直接参照しているため、該当トロフィーが二度と獲得判定できなくなる重大な影響があります。これは今回「廃止しない」とされている範囲です。

## 2. トロフィーとの重複調査

### 2.1 分類

**A. 獲得条件・役割がほぼ同じもの(12件、完全に1:1)**

`js/trophy.js` の `REFERENCE_TITLE_MAP` により、トロフィー**#101〜112**は称号12件をそのまま参照する「参照型」(新しい保存領域を持たず、`Storage.hasTitle()` を都度読むだけ)として実装済みです。

| トロフィー番号 | 対応する称号id | 称号名 |
|---|---|---|
| #101 | beginner | 国旗ビギナー |
| #102 | challenger | 国旗チャレンジャー |
| #103 | traveler | 国旗トラベラー |
| #104 | expert | 国旗エキスパート |
| #105 | master | 国旗マスター |
| #106 | legend | 国旗レジェンド |
| #107 | cap_beginner | 首都ビギナー |
| #108 | cap_challenger | 首都チャレンジャー |
| #109 | cap_traveler | 世界都市トラベラー |
| #110 | cap_expert | 首都エキスパート |
| #111 | cap_master | 首都マスター |
| #112 | cap_legend | 首都レジェンド |

**B. 一部重複するが、独自の価値があるもの**

- トロフィー**#1〜19**(挑戦の記録、19件全て)・**#40〜49,51,52,54,59**(国旗・首都制覇、計14件)は、称号システムの土台データ(`Storage.getAttempts`/`getBestRecords`/`hasTitle` 系)を**判定条件の材料として**使っていますが、トロフィー自体は称号とは別の新しい達成項目(回数の節目・正答率の節目・ダブル達成等)であり、1:1の重複ではありません。合計33件。
- 称号獲得画面・記念画像/賞状作成機能は、トロフィー獲得通知画面にはない「称号ブランドの演出」「画像生成・ダウンロード」という独自機能を持ちます。

**C. トロフィーとは異なる役割を持つもの**

- 称号コレクション画面の「記録」セクション(挑戦回数・最高正答率・問題数ごとの最高記録)は、トロフィー一覧のどこにも**表示そのものが存在しません**。トロフィーは「達成済みか否か」の二値情報ですが、この「記録」は生の統計値(回数・パーセンテージ・スコア)を継続的に見るための機能で、役割が異なります。

### 2.2 まとめ(重複度の全体像)

| 分類 | 件数 | 内容 |
|---|---|---|
| A(ほぼ同一) | 12件 | #101〜112がそのまま称号12件を参照 |
| B(一部重複・独自価値あり) | 33件 + 画面2つ | #1〜19・#40〜49,51,52,54,59がデータを利用。称号獲得画面・記念画像機能 |
| C(異なる役割) | 1機能 | 「記録」(挑戦回数・最高正答率・コース別ベストスコア)の統計表示 |

**称号システムの土台データ(Storage.TITLES/ATTEMPTS/BEST_RATE/BEST_RECORDS)に依存するトロフィーは、A+Bの合計で153件中45件(約29%)** に上ります。これが今回最も重要な発見です。

## 3. 廃止した場合の影響

「称号コレクション**画面**」だけを対象にした場合(データ・称号獲得画面・記念画像機能は維持する前提)の各機能への影響です。

| 画面・機能 | 影響 |
|---|---|
| ホーム画面 | 「🥇 称号コレクション」ボタン(`#btn-collection`)の削除・非表示が必要。ボタンを消すだけなら他要素のレイアウトへの影響は無い(独立したボタン)。 |
| 国旗クイズ | 影響なし。全問正解時の称号獲得・称号獲得画面・記念画像ボタンはコレクション画面と無関係に動作し続ける。 |
| 首都クイズ | 同上、影響なし。 |
| 世界地図 | 影響なし(称号を一切参照していない)。 |
| 世界図鑑 | 影響なし(同上)。 |
| 世界の国どこかな？ | 影響なし(同上。ランキングも称号と無関係)。 |
| ランキング | 影響なし。 |
| ゲーム結果画面 | 影響なし。「🏅 称号を見る」「🖼 記念画像を作る」ボタンの条件分岐(`titleObj` の有無)はコレクション画面とは別ロジックのため維持される。 |
| 保存済みの称号データ | 画面を消すだけなら保存・読み込みのコード自体は変更しないため、データは消えない。消去する場合は45件のトロフィーが二度と判定できなくなるため、**今回は対象外**。 |
| 既存のトロフィーデータ | 画面削除の影響なし。前述のとおり称号データ自体を消すと重大な影響が出る。 |

### 3.1 単純に削除して問題ない部分

- `index.html` の `#screen-collection` セクション、トップ画面の `#btn-collection` ボタン。
- `js/app.js` の `renderCollectionScreen()`/`renderCollectionSection()` と、それらの呼び出し(`btn-collection` のクリックハンドラ)。
- `css/style.css` の `.collection-*` 専用クラス(他画面で未使用であることの確認が前提)。

### 3.2 慎重に変更する必要がある部分(削除してはいけない)

- `js/storage.js` の `TITLES`/`ATTEMPTS`/`BEST_RATE`/`BEST_RECORDS` 関連の保存キー・関数全て(45件のトロフィーが依存)。
- `js/quiz.js` の `TITLES`/`CAPITAL_TITLES` 定義、`getTitleByCount`/`getTitlesForMode`(トロフィー#101〜112・`isModeTitlePerfectEarned` 系ヘルパーが参照)。
- `js/app.js` のクイズ終了時の称号判定・記録処理(`awardTitleIfNew`/`incrementAttempts`/`updateBestRate`/`updateBestRecord` の呼び出し)。
- `#screen-title-award`(称号獲得画面)・`#screen-memorial`(記念画像/賞状作成画面)とそれらを動かすコード一式。結果画面からの導線(「🏅 称号を見る」「🖼 記念画像を作る」ボタン)も含む。
- `Storage.resetAll()` 内の称号関連キーの削除処理(トロフィーの称号参照系と一体でリセットされる既存仕様のため、リセット自体は変更不要)。

### 3.3 推奨する整理方法

1. **今回は何も削除しない**(指示どおり)。
2. 将来的に進める場合は、**「称号コレクション画面」だけを削除・統合し、称号データ・称号獲得画面・記念画像機能はすべて維持する**方針を推奨します。
3. 画面統合を行う場合、現在コレクション画面にしかない「記録」(挑戦回数・最高正答率・コース別ベストスコア)の表示場所が失われるため、トロフィー一覧画面(`#screen-trophy-list`)の上部(例えば `#trophy-progress-summary` の付近)に、国旗/首都それぞれの「挑戦回数」「最高正答率」を簡潔に表示する形で引き継ぐことを検討してください(データ自体は既存の `Storage.getAttempts`/`getBestRate`/`getBestRecords` をそのまま読むだけで実現でき、新しい保存領域は不要です)。
4. トップ画面の「🥇 称号コレクション」ボタンを削除する場合も、称号獲得画面・記念画像機能への導線(結果画面のボタン)は従来どおり残すため、称号を獲得する体験自体がユーザーから失われることはありません。

## 4. 将来のプロフィール機能に向けた調査

### 4.1 現在のデータ構造の課題

現在の保存データは**全て単一のプレイヤーを前提としたグローバルなlocalStorageキー**で管理されています。

- `js/storage.js` の `StorageKeys`/`CapitalStorageKeys`(称号・挑戦回数・最高記録)、`TROPHY_KEY`(トロフィー、`js/trophy.js`)、`FINDCOUNTRY_*`(ランキング・コレクション・コース進捗)、`ENCYCLOPEDIA_*`(図鑑の閲覧・地図連携・復習記録)など、**全てのキーに「誰のデータか」という次元(プレイヤーID)が存在しません**。
- `keysForMode(mode)` のように「モード(国旗/首都)」で分岐する仕組みは既にありますが、これは「プレイヤーを分ける」仕組みとは別物です。
- 「世界の国どこかな？」のランキング(`FINDCOUNTRY_RANKING_KEY`)には名前を入力する機能(`FINDCOUNTRY_NAME_MAX_LENGTH`)がありますが、これは**その場限りの自己申告の文字列**であり、継続的なプレイヤーアカウントではありません(同じ名前で何度でも登録できる、名前からプレイヤーのデータを引けない)。

この構造のまま複数プレイヤーに対応しようとすると、「今ブラウザを使っている人が誰か」を判別する手段が無いため、**全プレイヤーが同じトロフィー・称号・記録を共有してしまいます**。

### 4.2 データ移行時の注意点

1. **キー名にプレイヤーIDを後から挟み込む設計**(例: `wfq_v1_trophy_earned` → `wfq_v1_p{playerId}_trophy_earned`)は、既存ユーザーの今あるデータ(プレイヤーIDという概念が無かった頃のデータ)をどのプレイヤーに割り当てるかという移行処理が必須になります。
2. 推奨する移行方針は、**既存のキー(プレイヤーIDなし)を「最初のプレイヤー」のデータとしてそのまま扱い続け、2人目以降のプレイヤーだけに新しいプレフィックス付きキーを割り当てる**方式です。これなら既存ユーザーは「プレイヤー1」としてアップデート後もシームレスに今までのトロフィー・称号・記録を失わずに使い続けられ、既存キーの読み書き処理(大量にある `Storage.*` 関数全て)を書き換える必要もありません。
3. 複数プレイヤーの「切り替え」機能を作る場合、`localStorage` のキー名を動的に切り替えるのではなく、`Storage` モジュールの内部で「現在選択中のプレイヤーID」を保持し、全てのget/set関数がそのIDをキーに織り込む形にすると、呼び出し側(`js/app.js`/`js/trophy.js`/`js/encyclopedia.js` 等、数十か所)を一切変更せずに済みます。
4. ランキング(`FINDCOUNTRY_RANKING_KEY`)のようにプレイヤーをまたいだ「全体ランキング」を今後も残したい場合は、プレイヤー別の個人記録と、全プレイヤー(端末内)共通のランキングを明確に別キーで管理する設計が必要です(現状は区別の概念自体が無い)。

### 4.3 既存利用者のデータを失わずにプロフィール機能を導入する方法

- 4.2-2で述べた「既存キー=プレイヤー1」の方針を取れば、アップデート直後に何かを変換・コピーする処理を一切実行せずに済み、データ破損・移行失敗のリスクを避けられます。
- プロフィール機能の初回起動時には、「今までのデータが引き継がれた1人目のプレイヤー」が自動的に存在する状態で始まるようにし、ユーザーに「プレイヤーを作る/選ぶ」操作を強制しない設計が安全です。

### 4.4 称号データを保持すべきか

**保持すべきです。** 2章で確認したとおり、称号データは153件中45件のトロフィーの判定材料として現役で使われています。プロフィール機能を導入してプレイヤー別管理に移行する際も、称号データ(TITLES/ATTEMPTS/BEST_RATE/BEST_RECORDS)はトロフィーデータと同じ粒度(プレイヤーごと)で一緒に移行する必要があります。称号コレクション**画面**を将来削除したとしても、データそのものは消してはいけません。

### 4.5 将来の実装に向けた推奨事項・避けるべき設計変更

- **避けるべきこと**: 今の段階で、特定の機能だけ「プレイヤーID」を先取りして他と異なる保存形式にすること(一貫性が崩れ、後の移行が複雑になります)。
- **避けるべきこと**: `Storage.*` の呼び出し側(`js/app.js`/`js/trophy.js`/`js/encyclopedia.js`/`js/map.js`/`js/review.js`/`js/findcountry.js`)に、localStorageのキー名を直接文字列で組み立てて参照するコードを新たに増やすこと。現状は幸い、全ての読み書きが `js/storage.js` の `Storage` オブジェクトや各種キー定数を経由しており、これを徹底しておけば、将来`Storage`内部だけでプレイヤー切り替えを吸収できます。
- **推奨**: 新しい保存データを追加する際は、今回の図鑑トロフィー機能(`wfq_v1_encyclopedia_*`)のように、必ず `js/storage.js` 経由の専用関数を用意するパターンを今後も踏襲すること。
- **推奨**: 「お気に入りトロフィーの選択」機能を作る場合も、トロフィーの獲得状態そのもの(`wfq_v1_trophy_earned`)とは別の保存キーに「選択したid一覧」を持たせ、トロフィーの判定ロジック(`js/trophy.js`)には一切手を加えない設計にすること(今回の図鑑トロフィーでの「閲覧記録」「獲得記録」を分離した設計と同じ考え方)。

### 4.6 SNS共有時の個人情報・プレイヤー名の配慮

- 現状の「記念画像・賞状作成」機能(`screen-memorial`)は、ユーザーが毎回手入力した名前(`memorial-name`、最大20文字)を画像に焼き込んで**端末にダウンロードするだけ**で、外部への自動送信・アップロードは一切行っていません。
- 将来「プロフィールや獲得トロフィーをSNSで共有」する機能を作る場合の注意点:
  - プレイヤープロフィールに保存した名前を、**ユーザーの明示的な確認なしに共有画像・共有リンクへ自動的に入れない**こと(現在の記念画像機能のように、共有する直前に毎回名前を確認・編集できるようにするのが安全)。
  - トロフィーの獲得日時(`earnedAt`)をそのまま共有すると、プレイ時間帯や生活パターンが推測できてしまうため、共有用の表示では日時を省略するか、大まかな年月までに留めることを検討する。
  - 複数プレイヤーが同じ端末を使う前提のため、共有操作を行う際は「今どのプレイヤーとして共有しようとしているか」を画面上で明確にし、別のプレイヤーのデータを誤って共有しない導線にすること。
  - 共有先(SNS)側の仕様によっては、共有した画像のメタデータ(EXIF等)に端末情報が残る場合があるため、共有用に生成する画像はcanvasで再描画した画像(現在の実装と同じ方式)を使い、元の写真等のメタデータを引き継がないようにする。
